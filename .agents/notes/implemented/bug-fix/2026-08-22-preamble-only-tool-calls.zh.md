# Agent Note：Gemini 系列模型的「只有前言」工具调用

Status: implemented

[English](2026-08-22-preamble-only-tool-calls.md) | 中文

## 问题

经由 OpenAI 协议网关接入的 Gemini 3.x 模型，经常发出这样一种工具调用：参数里只有一句自然语言摘要，完全没有必需的载荷——`bash` 收到 `{"description":"Check git status"}`，`run_code` 收到 `{"description":"Read the README"}`。JSON 格式完整、对象已闭合：模型宣告了这次调用，然后就停止生成，补全长度只有 16～30 个 token。`defineTool` 将其判为 `INVALID_ARGS`，这是正确的——没有任何东西可执行。

有两点让它从「吵闹」变成「昂贵」。

拒绝信息只告诉模型缺了哪个属性。在记录到的 107 次调用中，模型在下一次尝试中恢复的比例为 35%，而重复发出同样残缺调用的比例为 64%，最长出现过连续十一次失败，整个回合最终没有给出答案。

重复调用守卫看不见这个循环。它的链键是 `(tool name, canonical arguments)`，而 `description` 属于这些参数，因此同一条命令换三个标签就被算作三次互不相关的调用。实测证据：连续三次 `find . -name "*.go" -not -path "*/.*" -not -path "./vendor/*" | wc -l`，标签各不相同，没有触发任何提醒。残缺调用让情况更糟——它们各自携带不同的参数，因而会重置正在形成的链。

## 决策

三项改动，没有一项假装能修好模型本身。

### 让拒绝信息复述模型已经做出的决定

当违规项只有「缺失必填属性」，且参数中带有自然语言的 `description` 或 `title` 时，`ToolArgsError` 会追加一段指令，引用该摘要并点名缺失的内容：*You described this call as "Check git status" but sent no "command". Issue the same call again now with "command" filled in; the description on its own runs nothing.* 不符合这一形态时，消息仍是原本的违规列表，保持不变。

关键在于复述模型自己的摘要。模型此前已经选定了要做什么；仅有违规列表并不能告诉它这个选择仍然有效，于是它会推倒重来，而不是把这次调用补完。

### `bash`、`pwsh`、`run_code` 的 `description` 改为可选

该字段仍留在 schema 中——它是卡片标签——但只带载荷的调用现在可以执行。反向的残缺调用是真实存在的：模型也会发出没有 `description` 的 `code`，此前会因为缺少标签而被拒绝，那是 harness 自己制造出来的失败。缺少时，bash 卡片省略描述槽位；`run_code` 卡片退回到程序的第一行非空文本，与 bash 卡片直接使用命令本身的做法保持一致。

### 重复链比较的是「调用做了什么」

`ignoredArgumentKeys`（默认 `['description']`）会从链键中剥离展示型字段，且只剥离顶层，因此换了标签的重复仍算作重复，而嵌套的 `description` 仍属于载荷数据。结果带有 `INVALID_ARGS` 的调用对链透明：它们从未执行，而把它们计入只会重置那条在模型补全调用后立即继续的链。

## 证据

在同一网关上针对 `gemini-3.7-flash-high` 实测，覆盖全部四个预设：

| | 改动前 | 改动后 |
|---|---|---|
| 残缺调用在下一次调用中恢复 | 35%（n=107） | 68%（21/31） |
| 回合最终给出答案 | 出现最长 11 次的连续失败 | 6 / 6 |

残缺调用本身的发生率没有变化，这在预料之中：以上没有任何一项能阻止模型产生残缺调用。`Minimal` 模式在 3 次调用中一次都没有出现——它的 `bash` 来自 `tool-bash-persistent`，schema 只有 `{command}`——但仅凭 3 次调用说明不了什么。

## 影响

`bash`、`pwsh`、`run_code` 的 `description` 不再是必填。任何此前把它当作必然存在的组合，都必须允许它缺失：两张 shell 卡片会省略描述槽位，`run_code` 则从程序本身推导标题。改动之前记录的调用仍带有该字段，重放行为不变。

对于某一种违规形态，`ToolArgsError.message` 现在会随参数而变化。任何针对「缺失必填属性」失败文本做精确断言的地方，都会看到追加的修复指令；`violations` 与 `INVALID_ARGS` 代码保持不变，因此读取结构化错误的策略与路由不受影响。

重复守卫的计数方式发生了变化。此前依赖「换标签即重置链」的部署，现在会更早收到提醒；`ignoredArgumentKeys: []` 可精确恢复原先的链键。若某个工具的 `description` 确实会改变行为，默认设置会让它的链归类错误，需要在 `exclude` 中点名该工具，或清空该键列表。

残缺调用本身仍会作为失败调用抵达模型，仍会消耗一个 agent 步骤。要让它彻底不可见，需要备选方案中记录的「强制指定工具的重试」。

## 备选方案

**把 `description` 从 schema 中彻底移除。** 已实现、已测量、已回滚。促成这一想法的相关性是真实的——只有声明了 `description` 的工具会出问题，而 `read`／`skill`／`ask_user_question` 从不出问题——但因果方向搞反了。字段从 schema 移除之后，模型在 8 次调用中仍有 7 次发出 `description`，遗漏载荷的比例也没有变化。这个习惯属于模型，不属于 schema。移除该字段会让所有模型都失去卡片标签，却换不来任何东西。

**归咎于网关的流式聚合。** 已排除：用一条捕获到的请求直接重放到网关，`stream: true` 与 `stream: false` 各三次，两种传输方式下残缺调用出现的比例相同。是模型提前闭合了 JSON，下游并没有丢弃增量。

**在内部重试并强制指定工具。** 这是剩下最有力的方案，此处刻意未采用：用 `tool_choice` 锁定该工具重新发起请求，可以让残缺调用完全不可见，而且不消耗 agent 步骤。但 `tool_choice` 在 LLM seam 中根本不存在，采用它意味着扩展 Service Definition 与每一个 provider——这是一次 capability seam 改动，而相对于修复指令，它唯一多出来的收益只是隐藏一张卡片、省下一个步骤，因为模型在多数情况下已经能自行恢复。若恢复率被证明不够，此方案仍然可用。

**更换模型。** 部署方已否决：`gemini-3.1-pro` 表现出同样的行为，因此这是模型家族的共性而非某个模型的缺陷，而 flash 路线正是该部署想要的。

**削减注入的上下文。** 在两份相互独立的样本中，残缺调用率都与上下文大小相关——历史数据中提示 token 中位数为 27.8K 对 16.8K，而唯一没有出现残缺调用的预设，其单次请求约 1K，其他预设约 18K。这个杠杆是真实的，但它是关于「某个预设携带哪些工具与文档」的产品权衡，而不是缺陷，因此只作记录、不予改动。

**在重复守卫中采用模糊匹配。** 仍然否决，守卫自身的 Agent Note 早已记录了这一点。剥离一个已声明的展示型字段，属于对有意义参数的精确匹配；近似但不相同的命令仍会绕过链，在模糊匹配值回其代价之前，仍需要证据。
